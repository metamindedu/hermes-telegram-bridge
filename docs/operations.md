## Native CLI transport limits

- The renderer preserves the original helper argv envelope: UTF-8 JSON request bytes are capped at 22,500 and the base64url token at 30,000 characters. Values are never truncated or repaired; permanent local encoding/size errors do not launch the CLI, show user guidance, and suppress repeated attempts for the same ask fingerprint.
- Native result JSON is serialized as UTF-8 with `ensure_ascii=False` and capped at 24 KiB before the existing ASCII base64 frame. Full stdout remains capped at 48,000 characters, including frame markers and startup/log output.
- The native handler supplies this result budget internally; it is not renderer-controlled. `reply_poll` fits the whole response projection before changing a queued row to `applying` and returns at most one native apply claim per poll, so fragment assembly cannot age sibling claims. Ordinary answers retain the full descriptor/result response. An individually oversized response can use bounded fragment metadata; read-only `reply_fragment` returns allow-listed chunks for the exact owner/id/claim after current-boot, absolute-TTL and 45-second claim-deadline checks. It does not change schema, claim again, extend expiry or refresh the claim lease. Unselected forms remain `queued`.
- The Desktop assembles a bounded chunk count/byte total, verifies exact SHA-256 bytes and strict JSON shape, then repeats the existing live immutable identity/deadline checks before one `request.answer`. Missing, malformed, corrupt or expired fragment data settles the attempted claim as unknown/expired and is never replayed.
- Native `approval_poll` measures the exact complete `{ok,items,terminal}` UTF-8 JSON projection before changing one queued row to `applying`. It observes all active rows first, returns at most one claim, and returns/defer terminal IDs without consuming a claim when the combined frame would overflow. Registration rejects a single non-fitting approval before sending buttons and routes it to command-free Desktop guidance.

## Fixed helper conduit (local source candidate)

The app-level helper keeps the fixed `--profile default desktop-telegram-bridge --request` argv and the native default-home/package-owner guards. When a verified already-open active local route and the unique default sender belong to the same connection, ordinary helper actions can reuse that captured public gateway, as `loaded` and recovery already do. They must not wait on a separately dialed default-profile pool merely because that route appears in inventory. Remote/closed/different-source foreground sockets cannot be borrowed; ordinary helpers retain their existing local-default routed fallback when no eligible active conduit exists. Recovery retains its stricter captured-target checks and no-cold-dial behavior.

A write is attempted through only one selected conduit. A lost/malformed response is never retried through another socket. This transport selection does not change child/RPC budgets, native approval choices, the 45-second owner/claim leases or final native authority checks. Reusing a live socket is not proof that CLI startup fits a lease; qualify exact native latency and actual Desktop behavior separately before operational acceptance.

## Native command approval inbox (1.7.0 candidate; unreleased)

The separate `approval-inbox/approvals.sqlite3` is not a schema extension to the clarify or followup stores. Its callback namespace is `hda:` with an opaque random token and a one-character `o` (once) / `d` (deny) action; command, session, queue IDs and credentials are never in callback data. Only the exact default bot, private-home owner, chat, topic, original bot-authored message ID and unchanged full card text are actionable. Inline/inaccessible/forwarded/edited/foreign/expired/duplicate taps are rejected without creating a receipt or changing approval state. Known/tombstoned approval-card text replies are consumed by successfully installed handlers and never interpreted by the bridge as approval or agent input. Whole-platform behavior when handler attachment fails is outside this guarantee; see the SDK boundary below.

The monitor requires a fresh local route, waiting runtime row, durable session identity, backend epoch, `srq-*` request, matching `approval.pending` queue ID, exact full request and pending fingerprints, and the pinned core dangerous-command producer key before registration, before every poll claim, and again immediately before dispatch. The helper uses the real pinned `tools.approval_detection.detect_dangerous_command`; it does not stub or copy the classifier. It accepts only once/deny. Desktop calls `approval.respond` with the frozen runtime `session_id`, exact queue `request_id`, `choice`, and explicit `all:false`. Only a numeric `resolved===1` is applied; zero is expired, malformed/other/timeout is unknown. It never falls back to `request.answer`, retries an ambiguous RPC, or writes permanent/session allowlists. A coalesced follower remains subject to the core's fresh-prompt behavior for once.

The native approval queue ID binds the core's first settlement; the current RPC contract exposes no server-side fingerprint CAS. After the post-claim snapshot, a read-only native `approval_claim_valid` action checks the exact owner/card ID/claim/frozen descriptor authority, applying row, live receiver boot/version/capability/destination, owner lease, claim deadline, absolute expiry, and current ingress enablement. The renderer validates its typed receipt and rechecks stop/deadline immediately before `approval.respond`. This is the last fresh local gate, not an atomic server-side fingerprint CAS or cross-service exactly-once guarantee. `approval.pending` does not expose the enqueue timestamp, so local card expiry is bounded by the configured profile `approvals.timeout` and a currently pending queue; the native queue remains the decision authority and rejects a late tap with `resolved:0`. The clarify one-hour minimum is not reused.

The receiver capability is enabled only when the unified helper/renderer version agrees and the existing private-chat receiver heartbeat is live. The candidate advertises `desktop-command-approval-v3`; old v2 receivers/helpers/renderers do not grant capability. No new Telegram polling consumer is created: approval callbacks and known-card text consumers are installed on the same PTB `Application` by the primary package. A normal safe Gateway restart loads new handler code; source replacement or plugin rediscovery alone is not an activation guarantee.

Review cards show the complete redacted literal command and description without Markdown stripping or truncation. Redaction omissions/collisions, non-NFC/unsafe controls, unavailable timeout, or a card above Telegram's single-message limit disable buttons; the fallback notification contains Desktop guidance, not a partial command presented as approval evidence. Sends use `protect_content:false`, a same-text edit with the keyboard retained, and no retry after an ambiguous send.

## SDK initialization failure and recovery

The bridge is not a whole-Gateway input firewall. Successfully attached known-card consumers reject stale replies even when optional actions are disabled, and malformed managed policy does not itself remove these consumers. If the SDK cannot attach even the reject-only guard after one bounded local retry, the bridge refuses readiness and no bridge approval/answer is delivered; the native host can still accept that reply as ordinary Telegram input. See `SECURITY.md` for this user-approved lifecycle limit. Do not reply to old cards during initialization/receiver failure; use Desktop, inspect the error, and recover the existing Gateway at a safe point. No core patch, private handler-store override, second poller, unbounded retry, or forced shared-process stop is used.

Recovery uses a captured public `host.getGateway().request()` on the already-open local socket. The active named profile can execute the fixed default-home CLI (`--profile default`); it does not require the default profile to be foreground. Recovery admission/restoration is restricted to the currently active local target because the public SDK cannot prove arbitrary nonforeground sockets are live without dialing them. Fresh nonforeground completions retain the existing ordinary all-profile notification path; they do not gain durable recovery. Ordinary question/attention classification and its no-replay policy remain unchanged.

It never dials another profile to look up a candidate and never invokes create/resume/activate/prompt methods. A candidate is restored only for the unchanged local route, runtime ID, durable key, `started_at`, epoch and complete contiguous replay from the original watermark. Missing/malformed/failed/truncated snapshots remain unverifiable until retry/TTL; a validated empty active list, changed identity, new work, pending requests, active children/processes/control state or todos cancels it. Claim and dispatch use revision/token CAS in `BEGIN IMMEDIATE` and the exact existing completion-v2 delivery dedupe key. An expired pre-dispatch claim may be superseded; a stale helper cannot pass the new token/revision. Once the delivery boundary is `dispatching`, helper loss, process crash, malformed receipt, or absence of a later receipt is uncertain and never replayed. Only a durable proof tied to the exact attempt's direct pre-request `httpx.ConnectError`/`ConnectTimeout` is retryable. The recovery-only client is fresh, direct, `trust_env=False`, non-redirecting and has zero transport retries; read/write/protocol/JSON uncertainty and Bot API rejection are terminal. A failed verification edit after a confirmed send leaves it sent. No retry behavior changes for attention, replies, followups, or approvals.

Turning service or completion notifications OFF retires pending/read-blocked/claimed/proven-unsent candidates before a public settings path can turn them back ON. Dispatching candidates and writes already in flight are not revocable. A config OFF→ON edit made entirely outside the observed settings path cannot be detected retroactively; it is not permission to revive old candidates. Read-only `sender` counts are separate from the existing receiver heartbeat and expose no content or identifiers; neither is proof of a real Telegram delivery.

The focused suites are `completion_recovery.test.mjs` and `test_completion_recovery.py`; CI must run them alongside every existing Node/Python suite. ## Clarify registration receipt loss (unreleased source maintenance)

A clarify card's absolute lifetime is distinct from the native helper deadline and the 45-second transport lease. `reply_register` persists and publishes the card before returning its ID. A lost response, a post-registration structured error or an unbound duplicate can leave a real card unknown to the renderer. Owner-wide polling must not interpret that missing local binding as proof that the native question disappeared. A later healthy snapshot does not prove which historical error retired a specific old card.

The current source sends explicit `absent` IDs separately from observed and unverified IDs. Only a positively identified absence is terminal for that reason. Unmentioned open/queued forms lose ingress freshness, not their original TTL or frozen answers; they cannot accept answers or create application claims while unverified. Absolute TTL, receiver-boot changes, posting/applying lease lapse and ambiguous application no-replay remain unchanged. Mixed old renderers that omit `absent` leave unmentioned forms unverified rather than implicitly granting them authority.

## Approval observation gaps and registration bookkeeping (source maintenance)

An approval inbox row's `seen` is a freshness/publication observation, not a terminal-transition timestamp. A terminal card plus a later matching live native request proves a lifecycle mismatch, but cannot establish the exact historical expiry time or whether the original CLI receipt was lost. Keep those conclusions separate from deterministic injected-failure tests.

Unmentioned or explicitly unverified **open** approvals lose ingress freshness without being treated as positively absent. That inert marker must survive the next prune/owner-heartbeat operation; buttons still cannot queue choices until an exact fresh observation restores normal freshness. Original absolute expiry, owner/receiver lease gaps and boot/destination changes remain terminal. Queued choices are rejected and applying/dispatching uncertainty remains terminal/no-replay; these states are not rescued as open cards. Explicit native absence and immutable mismatch still retire the exact card.

For legacy queue/server-request registration only, the renderer retains the exact attempted registration if a write receipt is ambiguous, malformed, an unbound duplicate or an unknown structured error. A separate `approval_registration_lookup` uses a read-only SQLite snapshot and requires the complete original descriptor/request/pending fingerprints, same owner, fresh receiver/destination, completed publication, unexpired open/queued state and no application claim. It cannot send, flush, prune, renew freshness, reset expiry, adopt another window's card or revive terminal state. The renderer revalidates the live native snapshot before ordinary observation/claim/final-write checks. Existing CLI deadlines and canonical registration bookkeeping are unchanged. This does not repair already-terminal operational rows; answer those requests in Desktop. Native CLI/SQLite fixtures use mocked Telegram transport and are not installation, activation or human callback evidence.

Registration bookkeeping is retained for at most two minutes from the original attempt and is released on verified native request/session absence or a non-waiting parent. This local lookup budget does not change the native card's original expiry. Cleanup runs before heartbeat I/O too, so an unavailable receiver cannot retain the raw payload indefinitely; only the minimal same-request no-replay fence remains while that request is still present. A read failure or `found:false` alone is not proof of native absence. `approval_store_unavailable` can follow successful publication and a failed subsequent flush, so it remains uncertain and must not trigger another registration write or a misleading no-button fallback card.

## Content-free approval diagnostics (source maintenance)

An accepted Telegram callback is not proof of Desktop dispatch. For new transitions, the local approval inbox keeps a bounded diagnostic journal: accepted callback (`queued`), claimed Desktop work (`claimed`), native canonical dispatch CAS (`dispatching`, canonical only), and the first terminal transition. Each event contains only stage/source, an allowlisted reason, previous/resulting status and Unix timestamp, keyed internally by the opaque local approval row ID. It never stores the command, chosen decision, token, chat/user/session/route identity, fingerprint, raw receipt or exception. Renderer settlement reasons are caller-reported stage hints, not independently verified native receipts or new authority. No new Telegram messages or status-card text are added.

Reasons separate absolute expiry, observation/receiver/owner lease lapse, receiver rebound, native absence versus unverified observation, immutable mismatch, result budget, final renderer snapshot/claim/lifetime gates and unknown native RPC/receipt results. A valid weak `request.answer` ACK has its own unconfirmed-ACK reason and remains `unknown`; it is not a malformed receipt or proof of child completion. A same-identity receiver heartbeat gap records lease lapse rather than rebind; actual binding changes take precedence when both occur. Canonical live-claim loss, binding changes, invalid descriptors and store-read failure have separate fixed reasons. Existing TTLs, all authorization checks, terminal decisions and no-replay rules remain unchanged. A claimed event does not prove an RPC started; a missing event is not proof that no write occurred. Diagnostic storage is best effort: recoverable journal failures roll back only their savepoint. If SQLite aborts the whole decision transaction, the operation fails rather than falsely reporting a committed decision.

The journal is capped at 512 events total. Normal journal writes remove entries older than seven days and trim the count; read-only queries hide old/future-dated entries without deleting them. An idle database may retain expired metadata physically until the next journal write. First events for each row/stage are not overwritten while retained. Older rows are not backfilled: an empty journal cannot reconstruct the cause or exact transition time of an earlier incident. `seen` is still not the terminal timestamp. Clock rollback and incomplete/failed diagnostic writes limit chronology; diagnostics never participate in authority validation.

The fixed registered native CLI accepts a content-free read with **exactly** `{"action":"approval_diagnostics","capability":"desktop-command-approval-v6","id":"<32 lowercase hex local approval row ID>"}` inside the existing encoded `--request` frame. It remains under native package/home ownership validation and can be used with approvals disabled. It opens only the existing inbox using SQLite `mode=ro`/`query_only`, does not create a schema or missing directory, and never calls prune/heartbeat/flush/Telegram/native apply. The response distinguishes missing journal availability from store read failure and returns at most four safe events, never the approval descriptor. Do not pass an SRQ/session ID as the local approval ID or revive/replay an old response to collect diagnostics.

This additive table is created only by the installed writer's normal inbox open. Source tests do not migrate operating stores. Rolling back the plugin leaves the unused journal table in place without modifying approval rows, receipts or tombstones. Installation, resident handler/Desktop activation and an actual human callback remain separate approval/verification gates; this instrumentation is not a proven repair of a historical Telegram network outage.

- CI: `.github/workflows/tests.yml` runs those explicit suites on Windows and Ubuntu with pinned immutable Hermes sources. It does not deploy, restart, upload secrets, or claim GUI verification on another PC. Independent Heavy review and commit-bound CI remain separate release gates.

- Fake-home native-install tests use only a mock for Git transport. They exercise Hermes' actual install/publication/manifest/Doctor/context contracts and preserve sentinels/IDs. No live Telegram calls occur.

### Approval servicing versus background work

The source scheduling fix starts existing owned-approval servicing alongside the ordinary sweep on the same existing interval. Completion recovery, another session's reads and reply delivery must not prevent the approval owner from reaching its own heartbeat/poll path. One in-flight promise coalesces interval and sweep callers across the entire approval pump, including claim/application/settlement; it is not a second consumer or another Telegram poller. Disposal still stops new work. The 45-second lease, fresh native snapshots, exact route/request/queue bindings, fixed authority modes, claim gates and no-replay rules remain unchanged. A suspended renderer, a slow approval path itself or an unavailable owner can still fail closed; this scheduling change is not a guarantee against every lease lapse.

An independent pump must also coordinate with card producers: Python `poll` evaluates all active rows for an owner, not just the IDs in the submitted observation list. Publication through local binding and the actual poll receipt therefore share a narrow local ordering fence. Each publication attempt invalidates an in-flight local observation token; an older view is deferred without calling poll, not submitted as if a newly queued card were missing. An unbound uncertain registration also defers polling while ordinary bounded bookkeeping recovery runs. The token is not native authority, does not renew any lease and is never sent as a substitute generation. The pump keeps its initial heartbeat and relies on poll's existing transactional owner/receiver checks, avoiding a redundant cold CLI heartbeat between its fresh observations and poll. Do not restore liveness by weakening unmentioned/unverified queued rejection, reviving terminal rows or replaying a write.

When a new journal says `choice_accepted` followed by `owner_lease_lapsed` without `claimed`, Telegram ingress succeeded but the owner did not claim before its lease failed. This establishes the rejection boundary, not which awaited operation caused that historical delay. Retain a deterministic blocked-sweep regression separately from real helper timing and human roundtrip evidence. Native text saying the attached client cannot answer approvals can also accompany `request.cancel` interruption; inspect the actual cancellation event before blaming an old app or changing its capabilities. Never retry a withdrawn protected write via another tool, revive a terminal card or lengthen authority merely to hide the symptom.
