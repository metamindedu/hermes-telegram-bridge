## Unified package contract

- `desktop-plugins/session-complete-telegram/` installs as `session-complete-telegram`; its Desktop entry remains `desktop/plugin.js`, and native CLI remains `desktop-telegram-bridge`.
- One `register(ctx)` declares both the fixed CLI command and one Telegram handler factory with the public Hermes SDK. Declaration remains pure for RecordingContext/admission. Runtime factory authority comes from captured `ctx.plugin_id`, physical package location, and `runtime.resolve_package_home`; imports stay package-relative without a second poller, broad `sys.path`, global module aliases, or core overrides.
- Gateway wiring is limited to the existing configured Telegram bot/private home and the default installed-owner path. Successfully installed handlers consume recognized stale/tombstoned cards even when optional actions are off. Existing profile, owner, bot/chat/topic/message, route/session/request/queue, TTL, lease, claim, no-replay and read-only validity checks remain in force.
- `plugins/desktop-clarify-telegram/` remains only as a clearly deprecated inert/no-factory compatibility stub. It is not a required or advertised install package. While that legacy ID remains effectively enabled, the unified factory and helper readiness return `legacy_package_migration_required`; no config cleanup, state deletion/copy, schema migration, or consent inheritance is automatic.
- Native settings live only at `plugins.entries.session-complete-telegram.settings`: `replies_enabled` (clarify + ordinary completion followups) and `approvals_enabled` (Allow Once/Deny), each declared as boolean with default `false`. The two gates are independent and never suppress outbound notification actions. Raw root/plugins/enabled/entries/settings types, unknown flags, and wrong-typed values fail closed. Reads use Hermes `PluginContext.get_config` at factory admission plus strict raw YAML validation and native `plugins.enabled`/`plugins.disabled` semantics; the plugin never writes user config.
- Package/helper/renderer/approval handshake version is **1.7.0** / `desktop-command-approval-v3`. v2/v3 mixed and cached combinations deny approval capability. Preserve all v2 approval authority checks, command-free fallback notices, exact original message/private owner/route/session/request/queue, `all:false`, no session/permanent grant, and ambiguous-write no-replay behavior.
- Minimum Hermes remains `>=0.21.5`; exact unrelated dependency pins remain unchanged.

## Approval coverage follow-on — 1.8.1 source candidate (unreleased, 2026-10-15)

This bounded source/test/documentation candidate keeps the package/recovery version at 1.8.1, leaves the public 1.8.0 SHA and immutable v4 fixture bytes unchanged, and preserves the existing `desktop-completion-recovery-v1` implementation and `loaded.version` compatibility value 1.8.0. The approval helper/receiver and renderer move together to `desktop-command-approval-v5`; old/cached v4 halves cannot register or apply the expanded capability. Existing `approvals_enabled` and all other user choices remain default-off and unchanged.

Eligibility is an exact live native `method:"approval"` request (producer authority, not dangerous-detector membership) plus one mode frozen at registration: (A) exact open srq + exact parent `approval.pending` row → `approval.respond {session_id, request_id:queue_id, choice, all:false}`; or (B) exact open srq + a healthy, structurally valid queue snapshot with no matching/conflicting row → `request.answer {id:srq, result:{choice, all:false}}`. Failed/malformed queue reads, invalid rows, duplicate IDs, or a same-request conflict never downgrade to B. The mode, full request fingerprint, parent-row/absence binding, route/connection, profile, runtime/durable session, epoch, owner, and current receiver/lease are rechecked through the last pre-write gate. A mode change terminalizes the old binding and cannot fall through to the other dispatcher. Only once/deny are emitted; no session/permanent or `all:true` grant is possible. IDs follow native formats: 12-hex srq, 32-hex queue UUID, and editor pattern IDs `editor-<32 hex>`.

A queue `resolved:1` is the native queue response receipt and `resolved:0` is expired/already settled; other/ambiguous responses are terminal unknown. For the request path, typed `status:"expired"` is expired while typed `status:"ok"` is only Gateway acceptance. Because the current compute-host relay can swallow a child error and still return parent `ok`, that receipt settles as terminal uncertainty, does not replay, and is not described as a child decision or command-completion proof. Secret/password/vault value-entry methods remain outside the binary command approval contract.

Review cards represent every field supplied by the full native request after the existing redaction/Unicode/control checks. The full literal command (including supplied Python body) and structured editor edit are shown; the user is not told that omitted plugin arguments or protected-write diffs are known. Single-card review remains bounded at 4,096 UTF-16 units: an unsafe/over-bound request gets Desktop-only guidance, never truncated text with buttons. Multipart approval is not introduced. No inbox schema migration or destructive ledger/tombstone cleanup is included.

RED coverage was established before implementation, then focused GREEN checks use actual current installed-core producer/request-answer/queue settlement contracts and real PTB callback dispatch with isolated fake homes; no live Telegram, user-profile write, native install, Gateway restart, or production action is part of this candidate. The installed current core is not the historical CI pin `74306c1…`; evidence must name which core actually ran. Full CI, independent Heavy review, release approval, installation, activation, and live roundtrip remain separate gates.
